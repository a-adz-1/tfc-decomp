Team Fortress Classic: three small fixes

A short brief from the TFC community on what the 25th Anniversary server build broke, what it costs the game today, and the three contained changes that would let TFC servers move to the 25th Anniversary server build, so players' 25th clients and the servers run the same code again.

The push bug → The ramp bug → What we offer →

1In one minute

TFC is still played every day: public servers, nightly pickups, leagues. The 25th Anniversary Update was appreciated: it gave us a client that runs well on modern machines. One change in the 25th server build has split the game in two.

The ask: three contained changes in the TFC game code, all measured on a real TFC server.
  1. trigger_push: restore the frame-time-independent push (the diff is already on your tracker).
  2. func_pushable: the same frame-time scaling was added there; restore the original behaviour.
  3. The "ramp bug" dead stop at high frame rates in pm_shared.c: a nine-line fix, verified bit-for-bit against the original movement everywhere else.

Players already run the 25th client. One update with these would let servers follow, which also removes a movement problem every 25th player has today (section 3).

2The push bug

In the 25th Anniversary tfc.so, push fields scale by the server's frame time. At a normal server rate a gentle shove becomes a rocket booster; players are fired into ceilings or skip the map's intended path. Dozens of classic maps built around push fields are unplayable on a 25th server.

Reported and labelled Team Fortress Classic on your tracker, with the changed lines posted by a community member:

  • #3651 trigger_pushes are way too strong (December 2023)
  • #3780 trigger_push scales inversely with frametime (May 2024)

Fix: restore the pre-25th behaviour for both entities in the TFC build (and DMC/Ricochet, which took the same change). Half-Life itself did not, which is why the bug is invisible there.

3What it costs beyond push maps

Because of the push bug, almost every TFC community runs the pre-25th server. That has a second cost that only shows up when you measure it:

  • The 25th client and the pre-25th server were built with different compilers. The movement code is the same, but its floating-point results differ in the last digits.
  • Movement is predicted on the client and checked on the server, so a 25th client on a legacy server is a little wrong every frame and is corrected by every server update. Ramps, slides and landings feel subtly off everywhere, not just on push maps.
  • We confirmed this with a movement harness that runs scripted scenarios through each game build: the two builds agree with themselves to the bit and disagree with each other. Our server plugin now works around it by running each player's move with the build their client predicts with; to get there we had to compile the movement with your own toolchain (GCC 5 in the Steam Runtime "scout" image).

Fixing the push bug makes this go away on its own: communities move to the 25th server and client and server agree again. Details of the measurement: Fixing movement.

4The ramp bug

Sliding along a slope at speed, the player sometimes stops dead a few units onto it. Not every time: the same jump works nine times and fails the tenth, which makes it worse, since you can never trust a ramp. It happens far more at high frame rates and has been called the "ramp bug" for as long as people have played. The cause is in PM_FlyMove: at tiny frame times the player trace reports the slope the player is already on again, at zero distance, and the code treats the repeat as a second plane. Either exit from there is a zeroed velocity.

The fix is nine lines before the plane is added: if it's (nearly) a plane already hit this move, don't add it; nudge the velocity off the slope and carry on. It has to be in both the client and the server to be seamless, which is why we're asking for it in pm_shared.c rather than keeping it server-side.

  • Full report with reproduction, measurements and the patch: Ramp bug report (GitHub issue: link once posted)
  • Verified: every other movement scenario in our harness is bit-identical with and without the change; only the dead-stop scenarios differ, and there the player keeps sliding. Running on our public servers.

5What we offer

  • Measurements and the movement test harness for all three changes.
  • Patches in whatever form is useful: against the public SDK, or as described on the tracker.
  • Two public servers (US and EU) and a community that can test any build within hours and report back properly. We already run these fixes live, so we know what to look for.

The community also keeps a list of things it would love to see added or fixed, which we can document properly if there's appetite: Counter-Strike 1.6-style crosshair options in the TFC client (largely a copy of what CS already has), frame-rate-dependent air strafing and command execution, wall sticking, a few class-specific fire and reload quirks, and the engine's default network precision. These three are the ones that split the community, so we're keeping the ask to them.

We'd be glad to work with whoever looks after Half-Life's games now, at whatever pace suits. The fixes we run today, with downloads and source, are on our server fixes page; the long write-up is the investigation.

It would be amazing to finally see a few of TFC's old kinks fixed in the game itself, after all these years. The community that still plays it every night would notice straight away, and would be genuinely grateful.
