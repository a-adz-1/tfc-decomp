Full-precision prediction

Why the OTFC servers send your own position and speed at full precision, what the change is, and how to make it on your server. It takes six lines in one file and no client change.

Why → Apply it → Server fixes →

1The change

In tfc/delta.lst, the clientdata_t block (the player's own state, sent only to that player), six fields now go out as full 32-bit values instead of rounded ones.

FieldValve's defaultStepNowStep
origin[0..2] (your position)21 bits × 1281/128 unit (0.0078)32 bits × 655361/65536 unit (0.000015)
velocity[0..2] (your speed)16 bits × 81/8 u/s (0.125)32 bits × 655361/65536 u/s

Everything else in the file is untouched, in particular the entity_state blocks that describe other players to you; those are drawn interpolated and don't feed your prediction.

2What delta.lst is

GoldSrc doesn't send raw floats. For every field the server multiplies the value by a factor, rounds it, and sends that many bits; the client divides it back. delta.lst is the table that says how, and the server sends the table to each client when it connects, so the client needs no change: the pre-25th and the 25th Anniversary clients both read whatever the server declares, up to 32 bits a field.

Valve's defaults date from modem days. A 21-bit position with a step of 1/128 unit and a 16-bit speed with a step of 1/8 u/s were a good trade then. On a modern connection the extra bits cost nothing you can measure.

3Why it matters

Your game predicts your own movement: every frame it runs the movement code itself, so you don't wait a round trip to see yourself move. When a server update arrives, the game throws away its guess from that point on, takes the server's position and speed as the truth, and re-runs the frames since. If the server's truth matches what the game predicted, nothing visible happens. If it doesn't, you get a correction.

With rounded fields the server's truth is never quite what the game predicted, even when both ran the same code on the same inputs: the server's own value had fractions the rounding threw away. Your speed comes back a multiple of 0.125 u/s, your position a multiple of 1/128 unit. So the game restarts from a slightly wrong state every update, up to 102 times a second, predicts from there, and gets nudged again next time. Each nudge is tiny. The sum is a faint, constant jitter that is worst exactly where speeds have fractional parts: ramps and slides, air strafing, landing from conc jumps. Players describe it as the game feeling "floaty" or "not quite crisp" without being able to say why.

Sending the fields exactly removes that layer entirely. After this change, the only reason left for a correction is that the client and the server actually computed something different.

How we found it. Raising the precision was meant to tidy up the last of the choppiness after the netcode work. It did more than that: with the rounding gone, a second, smaller mismatch became visible for the first time, the one between the 25th Anniversary client's maths and the pre-25th server's (different compilers, last-digit float differences). That led to OTFC Movement Fixes 0.4, which moves each player with the build their client predicts with. The rounding had been hiding it all along.

4Does it fix ramps on its own?

No, and the ramp fix doesn't need it either. They remove different things, and smooth ramps need all three layers:

  1. The same movement code on both sides, so the game's prediction and the server agree: Movement Fixes 0.4's per-client matching today; a patched client against a patched server tomorrow.
  2. Exact reporting (this page), so the agreement isn't rounded away in transit.
  3. The ramp fix, so neither side stops you dead on a slope in the first place.

With 1 and 3 but not 2, slides still carry a faint jitter from the rounding. With 2 but not 1, you get crisp corrections instead of fuzzy ones. With 2 and 3 but the fix only on the server, a catch still shows the ping-sized hitch, because the client predicted a stop.

5Cost

At most 81 extra bits, about ten bytes, per update to a player, and only for fields that changed (updates are delta-compressed). At 100 updates a second that is under a kilobyte a second per player, against a typical rate of 20–100 KB/s. The range is unchanged in practice: 32 bits at ×65536 covers ±32768 units and u/s, more than any map coordinate or any speed the engine allows.

6Apply it on your server

Edit tfc/delta.lst. In the clientdata_t block near the top, replace the six origin and velocity lines so they read:

clientdata_t none
{
	DEFINE_DELTA( flTimeStepSound, DT_INTEGER, 10, 1.0 ),
	DEFINE_DELTA( origin[0], DT_SIGNED | DT_FLOAT, 32, 65536.0 ),
	DEFINE_DELTA( origin[1], DT_SIGNED | DT_FLOAT, 32, 65536.0 ),
	DEFINE_DELTA( velocity[0], DT_SIGNED | DT_FLOAT, 32, 65536.0 ),
	DEFINE_DELTA( velocity[1], DT_SIGNED | DT_FLOAT, 32, 65536.0 ),

	DEFINE_DELTA( m_flNextAttack, DT_FLOAT | DT_SIGNED, 22, 1000.0 ),

	DEFINE_DELTA( origin[2], DT_SIGNED | DT_FLOAT, 32, 65536.0 ),
	DEFINE_DELTA( velocity[2], DT_SIGNED | DT_FLOAT, 32, 65536.0 ),
	...

(The originals are 21, 128.0 for origin and 16, 8.0 for velocity.) Keep a copy of the old file. The server reads delta.lst once at start, so restart it; a map change isn't enough. Works on the Valve server and on ReHLDS, with pre-25th and 25th clients alike. It is live on all OTFC servers.
